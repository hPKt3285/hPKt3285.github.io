A first GitHub Actions workflow

2026-11-09 · Kevin Lin

The workflow in hello-github started as a few shell checks pasted straight into the YAML. It worked, but the same checks were also written in the README for local use, and after the second edit the two copies no longer matched. Moving them into a script fixed that, and the YAML became small enough to read at a glance.

What the workflow does

It runs on every push and pull request, checks out the repository, prints the last few commits and then calls one script:

name: README checks

on:
  push:
  pull_request:

jobs:
  readme:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Show recent commits
        run: git log --oneline -5
      - name: Check README structure
        run: bash scripts/check-readme.sh

The script itself requires a title, at least one section, and no trailing whitespace. Each failure prints the reason and exits non-zero, which is what turns the step red.

Why the checks live in a script

  • CI and a local run execute exactly the same code, so a passing local run is meaningful evidence that CI will pass too.
  • The failure message is written once, in a language I can test on my own machine, instead of being split across YAML and a README snippet.
  • The workflow file stays short, which makes it easier to see what actually happens on each run.

Reading a failed run

The useful part of a failed run is the step log, not the red cross. A few things that helped:

  • Open the step that failed and read upwards from the exit — the first error is usually a few lines above the end of the log.
  • set -euo pipefail matters: without it a script keeps going after a failed command and can finish green with the wrong result.
  • Every step is a separate shell. A cd or an environment variable set in one step does not exist in the next one.

Line endings

Windows editors happily save shell scripts with CRLF endings, and Bash on the runner then fails on the shebang line with a message about a bad interpreter. The repository now keeps a two-line .gitattributes so this cannot come back:

* text=auto
*.sh text eol=lf

What I would add next

Nothing clever. A path filter so the workflow does not run for changes that cannot affect the README, and a second job that repeats the same script on windows-latest to see how the same file behaves on two runners.
